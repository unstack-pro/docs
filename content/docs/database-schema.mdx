**The auth tables are generated, not hand-written.** They are derived from your
Better Auth configuration, so you never define `user`, `session` or
`organization` yourself — you add your own tables alongside them.

Where that schema lives, and what it takes to change it, is the biggest
difference between the two editions. Pick yours with the switcher below — the
choice is remembered across every page in these docs.

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

The schema is TypeScript. `lib/db/schema.ts` is the canonical entry point —
`drizzle.config.ts` points `drizzle-kit` at it — and it re-exports
`lib/db/auth-schema.ts`. Your own tables go in `lib/db/schema.ts`.

`lib/db/auth-schema.ts` is generated by `bun run auth:schema` from the Better
Auth config in `lib/auth.ts`. Changes to the shape of the database are expressed
as SQL migrations under `drizzle/`.

```ts title="drizzle.config.ts"
export default defineConfig({
    schema: "./lib/db/schema.ts",
    out: "./drizzle",
    dialect: "postgresql",
    dbCredentials: {
        url: process.env.DATABASE_URL!,
    },
});
```

</Tab>

<Tab value="Convex">

The schema is `convex/schema.ts`, which spreads in the tables from
`convex/betterAuth/authSchema.ts` and layers additional indexes on top. Tables
are declared with `defineTable` and `v.*` validators, and indexes with
`.index("by_x", [...])`.

The auth tables live in your **main** Convex database rather than behind a
separate [Convex Component](https://docs.convex.dev/components), so your
functions can reference users, sessions and organizations directly with no
component layer in between. The Better Auth integration is
[kitcn](https://kitcn.dev), imported as `kitcn/auth`.

```ts title="convex/schema.ts"
import { defineSchema } from "convex/server";
import { tables } from "./betterAuth/authSchema";

export default defineSchema({
    ...tables,
    session: tables.session.index("userId_expiresAt", ["userId", "expiresAt"]),
});
```

</Tab>

</Tabs>

## Tables

Fourteen tables are shared by both editions. The Drizzle exports and the Convex
table names are both camelCase; the underlying Postgres table names are
snake_case.

| Model | Postgres table | Convex table |
| --- | --- | --- |
| User accounts | `user` | `user` |
| Sessions | `session` | `session` |
| OAuth / credential accounts | `account` | `account` |
| Verification tokens | `verification` | `verification` |
| Organizations | `organization` | `organization` |
| Custom org roles | `organization_role` | `organizationRole` |
| Teams | `team` | `team` |
| Team membership | `team_member` | `teamMember` |
| Org membership | `member` | `member` |
| Invitations | `invitation` | `invitation` |
| Two-factor secrets | `two_factor` | `twoFactor` |
| Passkey credentials | `passkey` | `passkey` |
| Rate-limit counters | `rate_limit` | `rateLimit` |
| Audit log | `audit_log` | `audit_log` |
| JWKS signing keys | — | `jwks` |
| Avatar blobs | `user_avatar` | — |

<Callout type="info">
`jwks` exists only in the Convex edition: Better Auth signs the JWTs that Convex
verifies, and the key set is stored in the database. The Postgres edition issues
its own sessions inside Next.js, so there is no key set to store.
</Callout>

## Direct Access

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

The Drizzle client in `lib/db/index.ts` is created with the full schema, so
relational queries are available on `db.query.*`:

```typescript title="lib/server/users.ts"
import { eq } from "drizzle-orm";
import { db } from "@/lib/db";
import { user } from "@/lib/db/schema";

export async function getUser(userId: string) {
    return await db.query.user.findFirst({
        where: eq(user.id, userId),
    });
}
```

Outside the app, any Postgres client works — `psql`, or a GUI — pointed at
`DATABASE_URL`.

</Tab>

<Tab value="Convex">

Because the auth tables are in the main database, query them like any other
table. Rows are keyed by the Convex document id:

```typescript title="convex/users.ts"
import { v } from "convex/values";
import { query } from "./_generated/server";

export const getUser = query({
    args: { userId: v.id("user") },
    handler: async (ctx, args) => {
        return await ctx.db.get(args.userId);
    },
});
```

To look up by a field instead, use one of the declared indexes rather than
`.filter()`, which scans the table:

```typescript
const row = await ctx.db
    .query("user")
    .withIndex("email_name", (q) => q.eq("email", args.email))
    .first();
```

Outside the app, browse and edit rows in the Convex dashboard's data browser.

</Tab>

</Tabs>

## Extending the Schema

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

Add your tables to `lib/db/schema.ts`, next to the re-export of
`./auth-schema` — never to `auth-schema.ts` itself, which is overwritten on
every regeneration.

```typescript title="lib/db/schema.ts"
import { pgTable, text, timestamp } from "drizzle-orm/pg-core";
import { user } from "./auth-schema";

export * from "./auth-schema";

export const project = pgTable("project", {
    id: text("id").primaryKey(),
    name: text("name").notNull(),
    ownerId: text("owner_id")
        .notNull()
        .references(() => user.id, { onDelete: "cascade" }),
    organizationId: text("organization_id"),
    createdAt: timestamp("created_at", { withTimezone: true, mode: "date" })
        .defaultNow()
        .notNull(),
});
```

Then generate and apply a migration — see [Applying Schema
Changes](#applying-schema-changes).

</Tab>

<Tab value="Convex">

Add your tables to `convex/schema.ts`, alongside the spread auth tables:

```typescript title="convex/schema.ts"
import { defineSchema, defineTable } from "convex/server";
import { v } from "convex/values";
import { tables } from "./betterAuth/authSchema";

export default defineSchema({
    ...tables,

    projects: defineTable({
        name: v.string(),
        description: v.optional(v.string()),
        ownerId: v.id("user"),
        organizationId: v.optional(v.id("organization")),
        createdAt: v.number(),
    })
        .index("by_owner", ["ownerId"])
        .index("by_organization", ["organizationId"]),
});
```

</Tab>

</Tabs>

## Applying Schema Changes

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

Two steps: generate a migration from the schema, then apply it.

```bash
bun run db:generate      # drizzle-kit generate — writes a SQL migration into drizzle/
bun run db:migrate       # drizzle-kit migrate — applies pending migrations to DATABASE_URL
```

**Migration files are always scaffolded by the Drizzle CLI and never created by
hand.** Hand-written SQL *bodies* are permitted, but only for DDL that
drizzle-kit cannot express — triggers and functions — and only via:

```bash
bunx drizzle-kit generate --custom --name=member_owner_guard
```

That writes the journal entry and an empty `.sql` file for you to fill in. Two
of the five migrations shipped in `drizzle/` are exactly that: trigger DDL
enforcing that an organization can never be left with zero owners.

<Callout type="error">
`db:push` exists but must **not** be used to apply schema changes.
`drizzle-kit push` diffs the schema straight against the database and skips the
`drizzle/` folder entirely, so custom trigger migrations never run and the
journal drifts out of sync with what is actually deployed.
</Callout>

<Callout type="warn">
`drizzle-kit` does not load `.env.local`, so `db:generate` and `db:migrate` see
`DATABASE_URL` as undefined when run bare. Export the file into the shell first:

```bash
set -a && . ./.env.local && set +a && bunx drizzle-kit migrate
```
</Callout>

After changing the Better Auth config in `lib/auth.ts`, regenerate the auth
tables before generating the migration:

```bash
bun run auth:schema
bun run db:generate
bun run db:migrate
```

The header of `lib/db/auth-schema.ts` lists compound indexes marked `port:` that
have to be re-applied after each regeneration — do that before `db:generate`, or
the migration will drop them.

</Tab>

<Tab value="Convex">

There is no separate migrate step. `bun convex dev` pushes schema changes to
your development deployment as you save them, and `convex deploy` pushes them to
production as part of the deploy.

`convex/betterAuth/authSchema.ts` is generated — regenerate it with
`bun scripts/generate-auth-schema.ts` after changing the Better Auth config in
`convex/betterAuth/auth.ts`. Keep your extra indexes in `convex/schema.ts`,
layered onto the spread tables, so a regeneration cannot wipe them.

</Tab>

</Tabs>

## Relationships

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

Declare a relation next to the table, then pull the related row in one query
with `with`:

```typescript title="lib/db/schema.ts"
export const projectRelations = relations(project, ({ one }) => ({
    owner: one(user, {
        fields: [project.ownerId],
        references: [user.id],
    }),
}));
```

```typescript
const row = await db.query.project.findFirst({
    where: eq(project.id, projectId),
    with: { owner: true },
});
```

</Tab>

<Tab value="Convex">

Convex has no join. Fetch the document, then fetch what it references:

```typescript
export const getProjectWithOwner = query({
    args: { projectId: v.id("projects") },
    handler: async (ctx, args) => {
        const project = await ctx.db.get(args.projectId);
        if (!project) return null;

        const owner = await ctx.db.get(project.ownerId);

        return { ...project, owner };
    },
});
```

</Tab>
