**Understand the codebase so you can build your product on top.** Auth, organizations, and admin are already organized and working.

<Callout type="info">
You don't need to modify the auth system. Focus on the `/app` directory where you'll build your product features.
</Callout>

## Root Structure

Almost everything is shared between the two editions:

```
├── app/                    # Next.js App Router pages
├── actions/                # Server actions
├── components/             # Reusable React components
├── config/                 # Configuration files
├── emails/                 # Email templates (React Email)
├── lib/                    # Utilities and core logic
├── patches/                # Bun patch files applied on install
├── public/                 # Static assets
├── schemas/                # Validation schemas (Zod)
├── scripts/                # Build and utility scripts
├── styles/                 # Global styles
├── types/                  # TypeScript type definitions
├── video/                  # Remotion demo-video project (own deps)
└── ... config files
```

The difference is one directory and a couple of root files. Pick your edition
with the switcher below — the choice is remembered across every page in these
docs.

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

```
├── drizzle/                # SQL migrations + meta/_journal.json
├── drizzle.config.ts       # Points drizzle-kit at lib/db/schema.ts
└── proxy.ts                # Stamps the request path onto a header
```

There is no `convex/` directory. Better Auth runs inside Next.js, so everything
server-side lives under `app/`, `actions/` and `lib/`.

<Callout type="info">
Next 16 renamed `middleware.ts` to `proxy.ts`. This one stamps the current
request path onto an `x-current-path` header so Server Components can build
redirect targets that point back at the page the user was actually on.
</Callout>

</Tab>

<Tab value="Convex">

```
└── convex/                 # Convex functions, schema and Better Auth
```

There is no `drizzle/`, no `drizzle.config.ts` and no `proxy.ts`.

</Tab>

</Tabs>

## Actions Directory (`/actions`)

Server actions for server-side operations. How much lives here is the single
biggest architectural difference between the editions.

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

```
actions/
├── admin.ts                # Admin panel mutations
├── organizations.ts        # Organization, team, role and invitation mutations
└── users.ts                # Account, session, 2FA and passkey mutations
```

**Every write goes through a server action.** There are no live queries in this
edition: Server Components read through `lib/server/*`, and after a mutation the
client calls `router.refresh()` — or invalidates the relevant React Query key —
so the Server Component re-reads and the UI catches up. If a write succeeds but
the screen doesn't change, a missing refresh is the usual cause.

</Tab>

<Tab value="Convex">

```
actions/
└── update-profile-picture.ts
```

Almost nothing is here because almost nothing needs to be. Writes are Convex
mutations called from the client, and reads are reactive `useQuery` subscriptions
that re-render on their own when the underlying data changes. Server Components
read through preloaded queries instead.

</Tab>

</Tabs>

<Callout type="info">
Server actions provide type-safe server-side functions callable from client components.
</Callout>

Where Better Auth is configured, and what has to exist to reach it, is the part

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

```

├── auth.ts                 # The single betterAuth() instance

</Tab>

<Tab value="Convex">

```

├── auth-helpers.ts         # Auth utility functions

Better Auth itself is configured in `convex/betterAuth/auth.ts`, not here — the

</Tab>

</Tabs>

## File Conventions

### Loading States

`loading.tsx` files provide loading UI:

```tsx
// app/admin/loading.tsx
export default function Loading() {
  return <Skeleton />
}
```

### Error Boundaries

`error.tsx` and `global-error.tsx` files handle errors:

```tsx
// app/global-error.tsx
export default function GlobalError({ error, reset }) {
  return <ErrorUI error={error} retry={reset} />
}
```

### Layouts

`layout.tsx` files wrap route segments:

```tsx
// app/account/layout.tsx
export default function AccountLayout({ children }) {
  return (
    <div>
      <Sidebar />
      {children}
    </div>
  )
}
```

### Component Organization

**Pattern:** `_components` folders for route-specific components:

```
app/admin/
├── page.tsx
└── _components/            # Admin-only components
    ├── users-table.tsx
    └── admin-stats.tsx
```

<Callout type="info">
Underscore prefixed folders are not treated as routes by Next.js.
</Callout>

## Adding New Features

### New Route

1. Create folder in `/app`
2. Add `page.tsx`
3. Add `layout.tsx` if needed
4. Create `_components` for route-specific components

### New Component

1. Add to appropriate `/components` subfolder
2. Export from component file
3. Import where needed
4. Keep reusable, not route-specific

### New Data Operation

<Tabs groupId="edition" persist items={["Postgres", "Convex"]}>

<Tab value="Postgres">

For a **read**: add a function to `lib/server/`, and call it from a Server
Component.

For a **write**:

1. Create or extend a file in `/actions`
2. Mark it with `'use server'`
3. Export an async function that validates its input and checks the session
4. Call it from a component, then `router.refresh()` so the Server Component
   re-reads

</Tab>

<Tab value="Convex">

1. Create a file in `convex/`
2. Export a `query`, `mutation` or `action` with `args` validators
3. Read it from a component with `useQuery`, or call it with `useMutation`

Server actions in `/actions` are for the few operations that need Node APIs the
Convex runtime does not have.

</Tab>

</Tabs>

### New Email Template

1. Create in `/emails`
2. Use React Email components
3. Add to email sending logic
4. Test in development

## Best Practices

1. **Co-location**: Keep related code together
2. **Separation**: Separate UI from logic
3. **Reusability**: Extract reusable components
4. **Type Safety**: Use TypeScript everywhere
5. **Server Components**: Default to server, client when needed
6. **Actions**: Use server actions for mutations
7. **Validation**: Validate all inputs with Zod
8. **Error Handling**: Handle errors gracefully

## Development Tips

- Use `_components` for route-specific components
- Keep `components/` for truly reusable components
- Server Components are default, add `'use client'` when needed
- Use path alias `@/` for clean imports
- Follow existing patterns for consistency
